What this repo does

A menu-bar Mac app. It reads the focused text field through Accessibility, asks a small llama.cpp model running in-process for the next words, and draws them as grey text at the caret. Tab types them in. Korean works through real 2-set key presses. It keeps only counts.

Load I assumed: one person on one Mac, typing up to about 10 keys a second, with one model loaded. "Scale" here means per-key latency and memory, not many users.

What I read in full: all of Sources/ (HalftypeCore, HalftypeEngine, HalftypeApp, about 4,600 lines), Package.swift, the README, docs/how-it-works.md, AGENTS.md, and the test list in Tests/HalftypeAppTests/PureTests.swift (129 tests). I also grepped scripts/ and the learn branch's lab/dogfood/ab.py.

Must fix

1"Shown" counts every streamed token, not every suggestion Watcher.swift:417, 449, 475

What this is
Each suggestion gets a number, so Stats can count it "shown" once and "taken" once. stats.json keeps these per day. lab/dogfood/ab.py on learn divides taken / shown to compare days with the personal model against days without it.
Problem
The engine streams. After the first word passes the gate, it calls back each time the text grows (Engine.swift:170). Every callback runs received, which does suggestionNumber += 1. Every draw then sees a new number and calls onShown. So a 3-word suggestion streamed in 3 steps counts as shown 3 times. A Tab in the middle of a stream can also count as "taken" twice. No test checks how many times onShown fires.
Fix
Number the suggestion by its request, which stays the same for the whole stream and only goes up: 
-        suggestionNumber += 1
+        suggestionNumber = id  // One request is one suggestion, however many times it streams.
Add one test: a fake completer that streams three results for one request, and expect one onShown.
If we skip it
The Stats page itself is fine: it shows Tabs, letters and share by Tab, which don't use shown. But every shown in stats.json so far is too high, and the A/B take rate is too low. The personal model is the one method that moved keys saved, so a skewed A/B could hide a real gain or loss, for example when the personal model writes longer suggestions.

Should fix

2The rule that marks a day "with" or "without" the personal model has no test App.swift:100–110

What this is
count() decides, on every counted event, whether today ran with the adapter, without it, or mixed. Only days that are wholly one or the other go into the comparison (Tally.sum(personal:)).
Problem
It is a three-way branch with a known shortcut: comment, and it can't be tested as written. It reads engine?.applied, and engine is set only when the completer is a real Engine (engine as? Engine, App.swift:456), so a fake model never reaches the branch. One example of a mistake it would hide: if applied == wanted were flipped, every Compare day would be marked mixed, the comparison would have no days, and the Stats card would just never show.
Fix
Move the decision into a static function, the way this file already does with App.line and App.icon, and test its three cases: 
/// nil: mark nothing yet. Some(nil): a mixed day. Some(x): a day wholly with or without.
static func personalMark(hasAdapter: Bool, applied: Bool?, wanted: Bool) -> Bool?? {
    guard hasAdapter else { return .some(nil) }
    guard let applied, applied == wanted else { return nil }
    return .some(applied)
}
If we skip it
A regression here quietly empties or skews the only number that says whether Personal Model, the planned paid feature, helps.

3Every key may redraw the whole window App.swift:56, 251; Window.swift:771

What this is
tally is a @Published property on App, and every view in the window watches App. Each character typed anywhere adds 1 to tally.days[today].typed.
Problem
While the window is open, each key makes SwiftUI rebuild Root, FieldPage, StatsPage (a chart plus 182 dots), ModelsPage (a file size check for each model) and GeneralPage (a folder listing for the adapter), all on the main thread. That is also the thread that draws the ghost. count() lists the adapters folder once or twice more on each key (adapterFile, then adapterToday). I did not measure this. It matters most in Try It, where people judge Halftype first.
Fix
Measure first: Instruments' SwiftUI template while typing in Try It. If the per-key work is over about 1 ms, move tally into its own small ObservableObject that only StatsPage watches, so typing redraws only the Stats card. If it's under 1 ms, leave it.
If we skip it
Probably nothing you can see. At worst, the main thread does extra work during typing in Try It, next to the ghost's one-frame timing.

6scheduleUpdate writes OneAtATime out by hand Watcher.swift:37, 207–213, 591–601

What this is
Both stop a hung app from building up a queue: at most one job waits on the watcher queue.
Problem
They are the same idea with one difference. scheduleUpdate clears its flag before it runs, so a notice that arrives during a slow read still gets its own read. OneAtATime clears it after. The difference matters for reads and doesn't for heal.
Fix
Make OneAtATime clear first (still at most one waiting, so still no backlog), and use it for both: 
-    private let updatePending = Atomic<Bool>(false)
+    private let updating = OneAtATime()
     func scheduleUpdate() {
-        guard !updatePending.exchange(true, ordering: .acquiringAndReleasing) else { return }
-        queue.async { [self] in
-            updatePending.store(false, ordering: .releasing)
-            update()
-        }
+        updating.run(on: queue) { [weak self] in self?.update() }
     }
 // OneAtATime.run:
-            work()
-            pending.store(false, ordering: .releasing)
+            pending.store(false, ordering: .releasing)  // Before: input during the work gets its own run.
+            work()
Update the doc comment and aBurstOfInputAgainstABlockedHostRunsOneRecoveryAndThenAgain to match. About −5 lines.
If we skip it
Two ways to do one job, and someone fixing one of them misses the other.

7Each token builds a vocab-sized mask and scans the logits twice Engine.swift:386–398

What this is
Pick.best picks the most likely allowed token and its log probability over all allowed tokens, which is what the gate needs.
Problem
It allocates [Bool](count: vocab) (262k entries for Gemma) for each token, then scans the logits a second time to sum. That is small next to a decode step (milliseconds), but it runs on every token.
Fix
One pass with a running log-sum-exp, and no mask: 
var best = -1, top = -Float.infinity, mass = 0.0
for t in 0..<logits.count where allowed(t) {
    let l = logits[t]
    if l > top { mass = mass * exp(Double(top - l)) + 1; (best, top) = (t, l) }
    else { mass += exp(Double(l - top)) }
}
guard best >= 0 else { return nil }
return Pick(token: llama_token(best), logprob: -log(mass), isEnd: isEnd(best))
About −3 lines. The engine tests would catch a mistake.
If we skip it
A fraction of a millisecond per token, and a 262 KB allocation per token on the engine queue.

Verdict

Healthy. Fix #1 first, then #2. On John's question, is it simple and elegant: mostly yes, and better than most code of this kind. The design keeps choosing the one mechanism over the many. Field text is compared instead of key events, so typing through, Backspace, smart quotes and late answers all take one path (Follow.check). One word rule (Word) serves the prompt, the gate, stopping and accepting. There is one raw prompt path with no per-model tables. A single generation counter settles every race between a read and a key. The core is pure and tested, and there is one dependency. The weight in Watcher and Keys is real edge cases, each with a reason and a test, not speculation. It is less elegant in three places. App is a 690-line grab bag: app delegate, settings, model loading, menu, icon, updates and counting. The counting side channel (suggestion numbers passed from the watcher to the tap to the panel to App) is the least clean part, and that is where the bug is. And the code is dense: long lines and comments in place of names make each file slow to read, even though each line is correct. If you split one thing later, pull model loading (open, lost, engines, afterFetch, loadingPath, about 120 lines) out of App. Not before it gets in the way.

Lean: about −20 lines possible, −0 dependencies.
